# 固定版式 EPUB 在 Apple Books 中的缺陷

五种缺陷在桌面浏览器或通用阅读器中不报任何错误，但在 iPhone/iPad 的
Apple Books 里会立刻暴露。每一种都按 **症状 → 根因 → 修法 → 防护** 列出。

前三种在一本真实的 15 页书上复现并修复；第四、五种是同一本书（及其后继
版本）在 iPhone 上反馈回来的。引号中的措辞是读者对问题的原话描述；§5 的
症状按反馈转述。

---

## 1. 某一页显示时被放大

**症状** — 读者说某一页"默认被放大" / 打开时是放大的，而其他每一页都
正常适配屏幕。通常只针对单独一页报告，但每一页尺寸不同的页面都会受影响。

**根因** — Apple Books 用**第一页的**图片/视口比例来缩放固定版式书籍。
任何自身图片尺寸不同的页面都会按其原始像素比例渲染，于是过大的页面被
放大了。

真实例子：13 页为 940x1672，另有两页为 1536x2752。那两张大图渲染得约
大了 1.6 倍（1536/940 ≈ 1.63）。

**修法** — 把**每一页**图片（包括封面）归一到同一块共享画布：用
`contain` 缩放、居中，并用与页面背景相同的颜色填充留边，使上下留白
（letterbox）看不出来。然后给每一页相同的、按该画布尺寸设置的
`<meta name="viewport">`。

画布选*出现最多*的那个现有页面尺寸，这样大多数页面完全无需重采样；
只有个别页面才缩放。`build_epub.py` 会自动完成这件事（`pick_canvas`、
`render_image`）。

**防护** — `check_epub.py` 从归档包中收集每一页的 viewport 和每个 JPEG
的像素尺寸，若任一集合存在多于一个不同的值就报错。

## 2. 旁白播放两次，间隔约 0.5 秒

**症状** — "音频是重音" / "两个声音一前一后说，间隔 0.5 秒"。注意这
*不是*同时重叠：同一个声音在几分之一秒后又开始了一次。

**根因** — 两个 `<audio>` 元素指向同一个文件，且都带 `autoplay`。因为
每个元素独立解码，一个会在另一个之后约 0.5 秒才开始。这种问题经典的
引入方式是一个"安全回退"：

```html
<audio id="pgAudio" src="01.mp3" autoplay/>          <!-- plays at t=0 -->
<noscript>
  <audio src="01.mp3" autoplay controls/>            <!-- plays at t≈0.5s -->
</noscript>
```

`<noscript>` **并非惰性**：在不运行脚本的上下文里（预渲染阶段——
Apple Books 解析整本书与缩略图时就是如此），回退分支是活的，两个
元素都会加载；当时两者都带 `autoplay`，于是都会播放。0.5 秒的偏移是
两条独立解码管线的启动抖动——正是这种"同一个声音、略微滞后"的特征，
才能判定该根因，而不是回声、重复的源文件或相邻页面的音频。

**修法** — 每页严格**一个** `<audio>` 元素，URL 只引用一次。在不用第二个
元素的前提下获得无 JS 回退：给那唯一的 `<audio>` 放上 `controls`，并用
CSS 把它藏到画布外；当属性仍在时，用 CSS 属性选择器把原生控制条显示
出来；当 JavaScript 确实运行时，移除该属性并改为显示自定义按钮。

```css
.pg-audio          { position: absolute; left: -9999px; opacity: 0; }  /* hidden */
.pg-audio[controls] { left: 6%; right: 6%; bottom: 16px; width: 88%;    /* shown */
                     height: 40px; opacity: .85; }
body.js .pg-btn    { display: block; }   /* custom button only with JS */
```

```js
audio.removeAttribute('controls');        // hides the native bar
document.body.className += ' js';         // reveals the custom button
```

在**不运行脚本的上下文**（预渲染、或脚本被关闭的阅读器）里，读者看到的
是原生控制条，而不是自定义按钮——`controls` 兜底就是为此保留的。事先
说明这一点，以免被误认为是 bug。另外，页面**不得带任何 `autoplay`
属性**（见 §5）：起播只能来自控制器。

**防护** — `check_epub.py` 在某页出现多于一个 `<audio>` 标签、包含
`<noscript>`、带有**任何** `autoplay` 属性、或多次引用其音频 URL 时
报错。

## 3. 书末多出页面

**症状** — 一本 15 页的书在 iBooks 中显示第 16、17 页，内容是一个链接
列表。"后面有16页17页"。

**根因** — 导航文档被以 `linear="no"` 放进了 spine，这是许多教程推荐的
做法。**Apple Books 忽略 `linear="no"`**，照样把该文档渲染为阅读页面。
更糟的是，导航文档是*可重排*内容（一个标题加一个链接列表），而书中其他
部分都是固定版式，于是它被重新分页，可能扩展成好几页——观察到的案例里
是两页。

**修法** — 让导航文档**完全不进 spine**。EPUB 3 只要求它在 manifest 中
以 `properties="nav"` 声明，并不要求它出现在阅读顺序里。阅读器自带的
"目录"菜单依然可用，因为它读取的是该 manifest 条目。

作为双保险，给 `nav.xhtml` 自己的 `<meta name="viewport">` 和固定版式
样式，这样即使某个阅读器坚持要显示它，也只占一屏，而不是重排成好几页。

**防护** — `check_epub.py` 在 spine 中包含任何 `linear="no"` 条目、或
任何带 `properties="nav"` 的 manifest 条目时报错，并报告阅读顺序长度，
使页数错误一目了然。

## 4. 翻页后旁白闪一下就停

**症状** — 翻页时书刚开始朗读，不到几分之一秒就安静下来；随后点页面上
的播放按钮，该页又能正常朗读。在 iPhone/iPad 上反馈为"翻页会播放一个
短暂的音然后暂停"。

**根因** — 控制器没有恢复路径。它只启动一次播放，设置一个"已播放"标志，
此后只对 `visibilitychange` 作出反应；一个无人要求的停止就那样停着了。
两种不同机制会产生同样的声音：

- **离开**的页面开始朗读（因为翻页的那次点击借用了手势），随后在页面
  隐藏时被暂停；
- **进入**的页面开始朗读，在翻页过渡完成时被阅读系统挂起，且没有任何
  东西再去重试它。

用 `--debug-hud` 构建可以区分二者：每页都有自己的时间线，读数中
`play ok` 紧跟着 `hidden` 的那一页就是发出声音的页面。

**修法** — `js/reader.js` 里一个小状态机：绝不在手势处理器内部启动
（延迟约 300 ms，让 visibility 决定，这样翻页的点击无法在它正离开的
页面上启动音频）；自动启动先以**静音探针**进行——被引擎 kill 即让路
（不再重试，避免听到"停 → 重播"），探针存活才解静音出声（见下）。晚于
1.5 秒落下的暂停**不**重试——到那时阅读系统多半已为自己的旁白接管了
音频会话，重试会导致同时播放两条流。

**来自真机的后续** — 该修法的第一版在约五秒内重试了四次，读者反馈
"疯狂 kill 和 play"：引擎大约在 0.2 秒处杀掉*每一次*自动启动，于是每次
重试只是重启旁白、随即又被杀。随后收紧为"kill 后只重试一次"，读者仍
听得到"播放 0.x 秒 → 停 → 重播"——那次重试本身就是可听见的重播。

现在的策略是**被 kill 即让路，不再重试**。自动启动先以**静音探针**进行
（`muted` 起播）：被引擎杀掉时全程无声，控制器直接让路（读数记
`killed at start - yielding (engine has the session)`）；探针存活约
`PROBE_MS`（550 ms）后回到 0 秒并解静音——这是引擎没有接管时 JS 轨道
接手的方式。显式点击按钮总是直接出声；已借到手势的启动只在引擎尚未
拒绝过本页时直接出声——一旦被 kill 过，连页面上的点按也退回静音探针
（不重播），只有显式点按清除拒绝状态。

**在 iPhone/iPad 上确认** — 采用 resolve-at-use 控制器后，每一页都播放
自己的录音。剩下的唯一缺陷是第一个词被截断：阅读系统在翻页过渡期间
挂起媒体，因此在该期间发起的启动会在约 0.2 秒处死掉。于是控制器在页面
出现后不到 `ARMED_MS`（400 ms）不启动，并且每当它解析到不同的页面元素
时都会重新武装；读数显示 `waiting out the page turn`，随后是
`playing`。晚几百毫秒启动，就是这台阅读器上"翻页即朗读"所要付出的代价。

读数也能区分两种根因。同一窗口内出现 `hidden` 行（或新读数里的
`paused(hidden)`）意味着页面被挂起（是我们自己造成的）；**没有它意味着
引擎抢占了我们**——即起播（`probe ok` / `play ok`）之后紧跟
`killed at start - yielding`、中间没有 `hidden`，这指向阅读系统为自己的
旁白持有音频会话。历史备注：当时该现象被怀疑与随书发布的 Media Overlay
轨有关；MO 已整体移除，**现行行为以真机复核为准**（若掐断随之消失，
此条即可收束）。

**防护** — 没有自动防护：`check_epub.py` 校验的是包，而不是运行时行为。
回归风险在控制器里，因此让每个触发都经由 `attempt()` 汇聚、重试预算
（仅针对被拒绝的启动）放在 `schedule()` 里，而不要新增 `play()` 调用点；
相关约束列在 `epub-anatomy.md` 中。

## 5. 首次打开 / 渲染缩略图时，整本书被依次播完

**症状** — 首次打开一本书（停在封面加载）时，整本书的录音从封面到尾页被
依次播了一遍；首次点开底部缩略图（触发整本预渲染）时，每渲染出一页就播
那一页的录音。

**根因** — 每页唯一的 `<audio>` 带 `autoplay="autoplay"`。Apple Books 会
在不运行脚本的**预渲染环节**解析 / 渲染整本书（首次打开、生成缩略图）；
`autoplay` 由引擎自行起播、不经控制器、不受任何可见性门槛约束——每页被
预渲染时立刻自播。仓库里早有旁证：§2 的 `<noscript>` 兜底音频「真的会
加载并播放」，证明这个不跑脚本的上下文存在，且媒体会在其中启动。

**附带伤害** — 显示页上原生 autoplay 先出声，控制器的静音探针再把它
静音 / 解静音——探针「让路前从未出声」的前提因此不成立（读数时间线上
能看到先有声、再有 `probe ok`）。

**修法** — 页面**完全不带 `autoplay` 属性**；起播唯一归控制器（自动起播
是静音探针，按钮是显式起播）。不跑脚本的上下文（预渲染）因此保持静默——
这正是想要的：那些上下文里没有任何东西应该出声。无 JS 阅读器里的兜底是
页面原生播放条点按（`controls`）。

**防护** — `check_epub.py` / `build_epub.py` 的同一批谓词在页面文档出现
**任何** `autoplay` 属性时报错，消息写明：预渲染 / 预加载上下文会自行
起播。若移除 autoplay 后仍有重复播放，剩下的嫌疑是阅读器把同一页预渲染
了两遍（prefetch）——两份副本都不再自动出声，用 `--debug-hud` 定位是哪
一份在出声。

## 值得了解的阅读器行为

- **预渲染环节不运行脚本。** 阅读器在首次打开 / 生成缩略图时解析页面
  **不跑脚本**：`autoplay` 与 `<noscript>` 兜底都在那里生效——这是 §2 与
  §5 的共同根源。正常翻页展示时脚本照常运行。
- **有些引擎在页面本身被触摸过之前拒绝播放**（真机实测）：翻页无声，
  按钮可用。控制器在整个页面的生命周期内借用第一次手势，所以单次点按
  即可恢复；翻页自动播放在那里根本不可用。
- **旧副本会被缓存。** 重新导入修正后的文件不会替换书库里已有的那本书。
  务必先删除之前的副本，否则读者会再次报告同一个缺陷，而修复看起来
  毫无效果。
- **不运行 JavaScript 的阅读器（Google Play Books 等）整本无声**，属
  设计取舍，不是本书缺陷——参见 `playback.md`。Apple Books 的缺陷是
  *多余或错误的*播放；那类阅读器则是*没有*播放。
